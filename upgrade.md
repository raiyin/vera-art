## Промпт для агента-архитектора (обновление клиент-серверного приложения)

### Роль и контекст
Ты — **архитектор программного обеспечения** с опытом проектирования образовательных платформ. Перед тобой задача: спроектировать обновление существующего веб-приложения для художницы **Перцуковой Веры Олеговны**. Сайт уже работает, но сейчас требуется добавить полноценный функционал продажи обучающих курсов и мастер-классов по изобразительному искусству.

Существующий стек:
- **Фронтенд**: Nuxt.js (Vue 3, Composition API)
- **Бэкенд**: Go (net/http или фреймворк типа gin/echo)
- **БД**: SQLite (файловая)

Нужно спроектировать изменения, которые превратят сайт в образовательную платформу с ролями, платным контентом на срок, отзывами и чатом с преподавателем и другими важными аспектами необходимыми для успешной платформы по продаже.

### Требования к новой функциональности

#### 1. Управление доступом (RBAC)
- Роли: **администратор** (управление курсами, мастер-классами, пользователями, просмотр статистики) и **пользователь** (покупка, просмотр, отзывы, чат)
- Аутентификация с помощью JWT-токенов.
- Разграничение доступа на уровне API и UI (middleware в Go, guarded pages в Nuxt)

#### 2. Продажа курсов и мастер-классов
- **Курс** — может состоять из модулей/уроков (текст, видео, изображения)
- **Мастер-класс** — отдельное событие (запись единым блоком)
- **Покупка с ограничением по времени или навсегда**: пользователь получает доступ на N дней к купленному продукту или навсегда. По истечении срока доступ закрывается (или требуем продление). Нужна поддержка разных сроков (например, курс на 90 дней, мастер-класс на 30 дней)
- **Система оплаты**: интеграция с платёжным провайдером (например, ЮKassa, Stripe, Tinkoff). Нужно спроектировать логику создания платежа, обработку вебхуков, подтверждение оплаты и активацию подписки на срок. Поддержка промокодов.
- После оплаты пользователю открываются материалы, и запускается таймер доступа.

#### 3. Отзывы
- Пользователи могут оставлять отзывы на купленные курсы/мастер-классы (только после завершения срока или в процессе? Решай сам)
- Можно ставить оценку (1–5)
- Модерация: админ может скрывать/удалять нарушающие
- Вывод среднего рейтинга по продукту

#### 4. Чат с преподавателем
- Асинхронный чат (комментарии/диалог) внутри каждого купленного курса/мастер-класса
- Участники: пользователь (купивший) и преподаватель (админ = преподаватель)
- Сообщения: текст, прикрепление изображений (ограничение размера)
- Уведомления о новых сообщениях (можно через polling или WebSockets – выбери оптимальное для SQLite/Go)
- История чата сохраняется и привязана к конкретной покупке

#### 5. Дополнительные важные аспекты
- **Личный кабинет пользователя**: список купленных курсов с прогрессом (пройденные уроки), статусом доступа (активен/истек), кнопка продления
- **Прогресс обучения**: для курсов с уроками – метка “пройдено” для каждого урока
- **Админ-панель**: управление продуктами, просмотр платежей, ручное продление доступа, ответы в чате, модерация отзывов
- **Безопасность**: предотвращение подглядывания прямых ссылок на видео/материалы (подписанные URL или middleware проверки доступа)
- **Производительность**: SQLite справится, но нужно правильно индексировать таблицы (особенно для частых запросов: проверка прав доступа, список покупок, чат)
- **Миграции БД**: схема изменений должна быть описана в формате SQL (create/alter) или через миграции в Go

### Что требуется от тебя (архитектора)

Ты должен предоставить **подробное архитектурное решение** в следующей структуре:

1. **Модели данных (схема SQLite)**
   - Все таблицы с полями, типами, связями (около 10–15 таблиц: пользователи, продукты (курсы/мастер-классы), покупки (access), модули/уроки, прогресс, отзывы, чаты/сообщения, платежи, промокоды и т.д.)
   - Индексы и триггеры (если нужны для автоматического удаления просроченного доступа)

2. **API-эндпоинты (Go)**
   - Сгруппированные по модулям (продукты, покупки, оплата, отзывы, чат, админка)
   - Метод, путь, ожидаемые параметры/тело, ответы, код ошибки
   - Указать, какие роли имеют доступ

3. **Фронтенд-компоненты (Nuxt)**
   - Новые страницы и переиспользуемые компоненты (каталог, страница курса, плеер/текст урока, личный кабинет, форма отзыва, виджет чата, админ-панель)
   - Организация сторов (Pinia) для состояния: пользователь, корзина, покупки, чат

4. **Интеграция платежей**
   - Схема создания платежа, обработки вебхуков, верификации, временной активации доступа
   - Где хранить информацию о транзакциях

5. **Чат (real-time или polling)**
   - Рекомендации по реализации (например, long-polling из-за простоты с SQLite без лишних демонов)
   - Таблицы для сообщений, непрочитанных

6. **Стратегия проверки доступа к контенту**
   - Middleware/bouncer в Go: для каждого запроса на материал проверять, есть ли активная покупка -> срок действителен
   - Альтернатива: генерировать временные токены

7. **Миграция с существующей БД**
   - Предположи, что старые таблицы (например, пользователи) уже есть. Покажи примеры ALTER или новой схемы с префиксом, дай рекомендации по неразрушающему обновлению.

8. **Риски и компромиссы**
   - Ограничения SQLite (конкурентность на запись) – смягчения: очередь запросов, реже обновляемые таблицы вынести в отдельный файл? Или дать совет по переводу на PostgreSQL в будущем
   - Безопасность чата/файлов

### Формат вывода

- Ответ должен быть **структурирован** (заголовки, подзаголовки, списки, таблицы, блоки кода с SQL/Go/Nuxt).
- Для каждой таблицы пиши `CREATE TABLE` с комментариями.
- Для API – таблица с колонками: Метод, Путь, Описание, Доступ.
- Для фронта – описание маршрутов и компонентов без написания полного кода, но с указанием на логику.

### Дополнительные указания

- Учитывай, что художница (владелец) не технический специалист, но агент должен говорить на языке разработчика.
- Дай оценку сложности (человеко-дней) и приоритетность внедрения модулей.
- Предложи поэтапный план: сначала базовая оплата + доступ по времени, потом отзывы, потом чат.

Считай, что фронт уже умеет показывать статические страницы о художнице. Тебе нужно спроектировать только новые возможности. Пиши на русском, но код и SQL оставляй на английском.
